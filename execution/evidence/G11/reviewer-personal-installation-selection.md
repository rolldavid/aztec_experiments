# Personal-account App provisioning: bounded independent assessment

The smallest supported next experiment is an App-only selection step for the already-created partial repository 1419345087. It is not another generation request. This can test the missing selection capability without replaying either preserved create intent. Success is plausible, not established: the documented endpoint also requires administrator access, and the installation token normally cannot access repositories outside its selection. The October13 announcement describes organization use, whereas this application explicitly targets a personal User account.

The current API lists installation access tokens for `PUT /user/installations/{installation_id}/repositories/{repository_id}` and requires **GitHub App installation repository access write**; successful statuses are204/304. [GitHub installation endpoint](https://docs.github.com/en/rest/apps/installations#add-a-repository-to-an-app-installation). The exact permission key is `installation_repositories:write`. `repository_creation:write` is a separate new ability to create repositories, replacing broad Administration for that purpose; it does not itself grant installation selection. [October13 announcement](https://github.blog/changelog/2026-10-13-github-app-improvements-for-least-privilege-and-management/).

Security boundary: the new permission materially adds the ability to change installation selection; selected-only mode does not itself constrain this management capability to today's selected list. The trusted broker must restrict it to installation171412624 and its exact durable-created repository bindings. The narrowly proposed initial probe is existing partial1419345087; no arbitrary user-supplied repository IDs or all-repository selection.

Current reviewed broker e5cf527/449 accepts only Administration-write, Contents-write and Metadata-read (plus PR-write when connected mappings exist). It has no selection mutation or selection-purpose token. Merely changing the App permission will make its closed installation allowlist reject until the coherent code/config update is reviewed. Its HTTP204 handler is also deliberately restricted to disabling Actions; a selection step needs its own exact route/status projection, not a generic success relaxation.

Recommended bounded implementation within the existing broker:

1. Add only `installation_repositories:write` to the dedicated App and approved installation, preserving selected-only mode and exact User/App/installation IDs. Add an explicit closed purpose token for selection; do not give it to generated code or ordinary content operations. Do not introduce developer/PAT runtime credentials.
2. Bind selection to the existing durable creation record's numeric repository ID, intended name, owner and unique marker. For the existing422 partial result, use root's retained independently verified identity record: the broker could not obtain the private unselected repository through its restricted token. Never accept an application user's arbitrary repository ID as selection authority.
3. Persist one selection intent before the exact PUT. On uncertainty, enumerate selected repositories and verify exact ID/owner/name/private/marker; do not replay PUT just because a response is missing. Only after successful readback mint a new exact-repository token, disable Actions and verify it, then resume existing Git initialization/source publication. Empty repository initialization is a distinct durable action, not another generate request.
4. Preserve complete selected-inventory validation, including any newly selected partial repository now bound to its own creation intent. Do not enable all repositories or silently adopt unrelated names. Keep original403/422 attempts and assisted mirror evidence separate.

A token cannot be minted with access to repositories that its installation was not granted. Thus `repository_ids:[1419345087]` before selection is not a workaround. The new selection capability must be tried as its specifically documented installation operation; if the personal-account admin-access rule rejects it, record that exact response and stop, without broadening to all repositories. [Installation token scope](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app).

Adding `repository_creation:write` now is not necessary for the documented selection experiment because Administration already nominally covers creation. It may later narrow the generation token's authority, but there is no evidence it resolves422. If selection succeeds, qualify the full future provisioning path in a distinct authorized namespace once; first separate private metadata creation from Git initialization so an initialization failure is recoverable from the returned identity. That would be a coherent application provisioning change, not permission retry roulette. Both current template failures created metadata and omitted selection; their precise422 cause remains unknown because original error bodies were not retained. Do not label selection permission as the proven cause.

No API mutations, new credentials, source edits, or service changes were performed for this assessment. Automatic provisioning remains unqualified; the originalB assisted mirror is independently useful functionality.
