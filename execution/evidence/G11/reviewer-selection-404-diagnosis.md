There is no documented missing Administration requirement for that selection call. Its documented fine-grained requirement is installation_repositories write, and IATs are listed as supported; it additionally requires administrative access to the target repository. [Selection endpoint](https://docs.github.com/en/rest/apps/installations#add-a-repository-to-an-app-installation). An installation token cannot acquire access to a repository outside its installation selection merely by requesting that ID. [Token scope rules](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app). Therefore404 is consistent with an inaccessible private target, but does not uniquely prove that cause. Adding Administration to the same selection token is not a source-backed fix and should not trigger another mutation attempt.

The new repository_creation write permission is distinct. GitHub describes it as creating a repository in the account where granted; the new installation_repositories management description specifically mentions organizations. [October13 announcement](https://github.blog/changelog/2026-10-13-github-app-improvements-for-least-privilege-and-management/). Current REST documentation nevertheless lists IAT support for personal POST/user/repos with either Administration-write or Repository-creation-write, and template generation with Repository-creation-write plus Contents-read. This makes a creation-purpose token using the newly granted permission a documented mechanism worth implementing, but does not establish automatic selected-repository access or explain the earlier422. [Repository creation endpoints](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user).

Smallest coherent broker change:

- Bind an explicit expected installation-permission map in private configuration/journal. It may match the20 permissions the owner approved, but must not accept arbitrary observed additions. Current available() rejects the newly expanded installation before any normal operation. Preserve exact User/App/installation identity, selected-only mode, and dedicated repository inventory.
- Keep content, connected-PR, admin/settings and selection tokens independently minimal. Change only the creation-purpose token to repository_creation:write, plus contents:read if retaining the pinned template route. Validate its exact returned permissions; do not request all20 for convenience. This is the only materially new creation capability not exercised by current broker, which still requests Administration+Contents-read.
- Preserve every existing failed create/selection intent. No automatic route fallback or same-intent retry. A future explicitly authorized fresh namespace must be a distinct receipt and must verify returned private owner/name/marker, selected access, Actions disabled and complete Git initialization before source writes. Failure after metadata creation must retain numeric identity and stage; it must not create another repository to hide the failure.
- If choosing direct private metadata creation to avoid template-copy coupling, use auto_init:false and separate durable selection/initialization stages. Do not claim this guarantees access: if newly created private repository is still outside the installation and inaccessible, App-only automatic provisioning remains blocked. Do not install a developer token into the runtime or change all-repositories selection to bypass that boundary.
